# План: переход на клиент-серверную архитектуру с хранением данных в облаке

## Цель
Сделать приложение многопользовательским веб-приложением (как сейчас, без EXE), в котором все производственные данные хранятся на сервере, а пользователи заходят под логинами с ролями.

## Ключевые решения
- **Формат приложения:** остаётся веб-приложением в браузере. Lovable/TanStack Start изначально даёт серверный рантайм, поэтому для клиент-серверного хранения данных не нужен EXE — достаточно подключить бэкенд.
- **Бэкенд:** Lovable Cloud (Supabase): PostgreSQL, аутентификация, Row-Level Security, серверные функции.
- **Режим работы:** только онлайн (без офлайн-синхронизации).
- **Данные на сервере:** все — изделия, партии, договоры, участки, компоненты, операции, тех.маршруты, графы, привязки партий к договорам, нормы времени.

## Что нужно сделать

### 1. Включить Lovable Cloud и настроить аутентификацию
- Подключить Lovable Cloud к проекту.
- Настроить вход по email/паролю и Google OAuth (по умолчанию для Lovable Cloud).
- Добавить таблицу `profiles` (id → auth.users, display_name, role_title, department) и триггер на автосоздание профиля при регистрации.
- Добавить таблицу `user_roles` и функцию `has_role` (security definer), чтобы избежать рекурсии RLS.
- Роли: `admin`, `production_manager`, `workcenter_master`, `viewer`.
- Подключить middleware `attachSupabaseAuth` в `src/start.ts` для автоматической передачи токена на сервер.

### 2. Спроектировать схему базы данных
Перенести текущую модель из `src/lib/production/types.ts` в реляционные таблицы:

- `products` — изделие-шаблон (название, версия, архивность, примечание).
- `component_groups` — группы компонентов изделия (материалы, ЭРИ, оснастка, полуфабрикаты).
- `positions` — позиции внутри группы (наименование, количество на изделие, остаток, срок поставки, поставщик, примечание).
- `operations` — операции тех.маршрута (название, ответственный, длительность, порядок, входы, выход, участок, аутсорс, дни аутсорса, примечание).
- `operation_groups` — логические группы операций.
- `batches` — партии (изделие, номер, заказное количество, отгружено, срок, примечание, выполненные операции, локальная копия маршрута).
- `batch_completed` — нормализованная таблица выполнения операций по партиям (batch_id, operation_id, quantity).
- `contracts` — договоры (номер, контрагент, изделие, децимальный номер, дата подписания, примечание).
- `contract_deliveries` — сроки и количества поставок внутри договора.
- `delivery_batches` — связь many-to-many между поставкой и партией.
- `workcenters` — участки (название, количество рабочих, часов в неделю).
- `transfer_times` — время транспортировки между узлами (from_node, to_node, hours).
- `organization` — справочник сторонних организаций для аутсорса.

Каждая таблица `public` сопровождается `GRANT`, включением RLS и политиками доступа на основе ролей.

### 3. Настроить права доступа (RLS)
- `admin` — полный доступ ко всем таблицам.
- `production_manager` — чтение/запись изделий, партий, договоров, участков, норм времени.
- `workcenter_master` — чтение всего; изменение только `batch_completed` и `positions.stock` для своего участка (или всех, если участок не привязан к пользователю — уточнить при реализации).
- `viewer` — только чтение.
- Владелец данных (creator_id) может редактировать созданные им записи, если роль не даёт более широких прав.

### 4. Переписать хранилище на серверные функции
Создать `src/lib/production/production.functions.ts` с набором `createServerFn`:

- `getProducts`, `getProduct`, `createProduct`, `updateProduct`, `archiveProduct`.
- `getBatches`, `getBatch`, `createBatch`, `updateBatch`, `deleteBatch`.
- `setBatchCompleted`, `setBatchShipped`, `setBatchOrderedQty`.
- `getContracts`, `createContract`, `updateContract`, `deleteContract`, `addDelivery`, `updateDelivery`, `removeDelivery`, `attachBatchToDelivery`, `detachBatchFromDelivery`.
- `getWorkcenters`, `createWorkcenter`, `updateWorkcenter`, `deleteWorkcenter`.
- `getTransferTimes`, `setTransferTime`.
- `updatePositionStock`, `updateFixtureCount`.
- `getBatchRoute`, `getProductRoute`, `mutateProductRoute`, `mutateBatchRoute`, `resetBatchRoute`.

Все функции используют `requireSupabaseAuth` и работают от имени аутентифицированного пользователя через `context.supabase` (RLS).

### 5. Обновить React-клиент
- `ProductionProvider` переписать на TanStack Query: загрузка данных через `useSuspenseQuery`, мутации через `useMutation` + инвалидация кэша.
- Убрать локальные `useState` для products, batches, contracts, workcenters, transfers.
- Сохранить в локальном хранилище только тему оформления.
- Добавить `src/routes/auth.tsx` — страница входа/регистрации.
- Переместить защищённые страницы под `src/routes/_authenticated/` (интеграция Lovable управляет этим layout автоматически).
- Обновить `AppSidebar`: добавить меню пользователя (имя, роль, выход), скрыть кнопки, которые недоступны текущей роли.
- Добавить индикатор загрузки и обработку ошибок сервера на всех экранах.

### 6. Защитить маршруты и действия
- Главная страница, Изделия, Производство, Участки, Договоры, Настройки — требуют аутентификации.
- Редактирование тех.маршрута/графа и создание изделий/партий/договоров доступно только `admin` и `production_manager`.
- Отметка выполнения операций — `production_manager` и `workcenter_master`.
- Просмотр — всем аутентифицированным.
- Проверять права на сервере в каждой `createServerFn`, а не только в UI.

### 7. Миграция существующих данных
- Подготовить SQL-скрипт (через инструмент миграций Lovable Cloud), который создаёт таблицы и заполняет их текущими данными из `src/lib/production/data.ts`:
  - Изделия №1 и №2, их компоненты, операции, группы.
  - Партии `b-1-24`, `b-1-25`, `b-2-07` и выполненные операции.
  - Договоры `c-118`, `c-204` и поставки.
  - Участки и нормы транспортировки.
- Скрипт выполняется один раз при развёртывании схемы.

### 8. Обновить страницу настроек
- Убрать экспорт/импорт JSON как основной способ переноса данных (данные теперь на сервере).
- Оставить экспорт JSON в режиме «резервная копия» для администратора.
- Оставить переключение темы.
- Добавить раздел управления пользователями/ролями для `admin`.

### 9. Проверка и тестирование
- Проверить сборку и типизацию (`bunx tsc --noEmit` или `tsgo`).
- Проверить, что незащищённые серверные функции не утекают в клиентский бандл (нет импорта `client.server` из компонентов).
- Протестировать через Playwright: регистрация, вход, создание партии, редактирование тех.маршрута, привязка к договору, отметка выполнения операции.
- Проверить RLS: пользователь с ролью `viewer` не может изменить данные через прямой API-вызов.

## Результат
Приложение остаётся веб-приложением в браузере, но все данные хранятся в PostgreSQL в Lovable Cloud. Пользователи заходят по логинам, видят общие данные и имеют права в зависимости от роли. Локальное хранилище используется только для темы.
